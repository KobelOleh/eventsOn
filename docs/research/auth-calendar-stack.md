# Research: Auth.js + Prisma + FullCalendar + Server Actions stack (EventsOn)

Researched 2026-10-13 against primary sources only (official docs, first-party source code, npm registry metadata, one peer-reviewed paper). Every claim has a URL next to it. "npm registry" means `https://registry.npmjs.org/<pkg>` metadata read on 2026-10-13. Items marked "inferred" are my conclusions from primary material, not statements in it.

## Summary of recommendations

1. **Auth library.** `next-auth` v5 is still **beta only**: npm `latest` = `4.24.15`, `beta` = `5.0.0-beta.32` (published 2026-07-20). Official install: `npm install next-auth@beta`. The Auth.js project has **joined Better Auth**; its README recommends Better Auth for new projects, and Better Auth commits to security patches and urgent fixes only. Auth.js v5 fits all your constraints, but this is a decision to confirm (Open uncertainties #1). If you stay: pin `next-auth@5.0.0-beta.32` exactly.
2. **Next.js 16.4.0** (npm `latest`) renamed `middleware.ts` to **`proxy.ts`**, and proxy runs on **Node.js by default**, so Prisma/`pg`/native `bcrypt` may be imported there. Proxy must never be the only authorization layer (Server Actions can bypass it).
3. **Auth config.** Credentials + Google, `session: { strategy: "jwt" }` set **explicitly** (with an adapter Auth.js defaults to `"database"`), `PrismaAdapter` so Google users become real `User` rows your events can reference by FK. A split `auth.config.ts` is optional on Next 16.
4. **User id.** Put `user.id` into the token (`jwt` callback) and `session.user.id` (`session` callback); augment `Session` (module `next-auth`) and `JWT` (module `next-auth/jwt`). In every Server Action call `await auth()` and put `userId: session.user.id` in every Prisma `where`.
5. **Account linking.** Leave `allowDangerousEmailAccountLinking` **off** unless Credentials sign-up verifies email ownership (otherwise pre-hijacking). The default (error `OAuthAccountNotLinked`) is the official safe behavior.
6. **Prisma.** Stable is **Prisma 7.10.0**. Prisma 8 is RC, and the `prisma` npm `latest` dist-tag already points at `8.0.0-rc.22` (trap): install `prisma@7` / `@prisma/client@7`. Prisma 7 requires the `prisma-client` generator with explicit `output`, a driver adapter (`@prisma/adapter-pg`), `prisma.config.ts`, Node >= 20.19, TS >= 5.4. Search with `contains` + `mode: "insensitive"`; index `(userId, startAt)`; `pg_trgm` GIN only if measured.
7. **FullCalendar.** npm `latest` is **v7.1.2** (MIT for standard features). v7 puts everything under `@fullcalendar/react` subpath entries (`@fullcalendar/react/daygrid`, `/interaction`, ...) plus required peer `temporal-polyfill`, and ships no CSS. The old separate `@fullcalendar/daygrid` etc. are v6 (6.1.21). The React package contains no `"use client"`, so wrap it in your own client component. Fetch by visible range through an `events` function (or `datesSet`) that calls a Server Action.
8. **Server Actions.** Public POST endpoints: authenticate, authorize by ownership, validate with zod (current v4: the Next docs sample uses zod 3-only APIs), `useActionState` for forms, `revalidatePath` after writes. The client dispatches Server Actions **one at a time**, which matters for calendar navigation.
9. **Testing.** Vitest against a dedicated real Postgres (`prisma migrate deploy` in `globalSetup`), `vi.mock("@/auth")` for `auth()`, `vi.mock("next/cache")` because revalidation throws outside a Next request. Vitest 5 needs Node >= 22.12 (use Vitest 4 on Node 20).

## 2. Credentials + Google + JWT + Prisma adapter; config split; proxy

### What is required / allowed

- **Credentials needs JWT.** `@auth/core` `assert.ts`: if the strategy is `"database"` and the only providers are credentials it returns `UnsupportedStrategy("Signing in with credentials only supported if JWT strategy is enabled")` (https://github.com/nextauthjs/next-auth/blob/main/packages/core/src/lib/utils/assert.ts). The credentials branch of the callback handler always encodes a JWT cookie and never creates a DB session (https://github.com/nextauthjs/next-auth/blob/main/packages/core/src/lib/actions/callback/index.ts). With Credentials + Google the assert does not fire, but credentials logins still only work as JWT; so set `strategy: "jwt"` explicitly (conclusion from both files).
- **Adapter flips the default.** `init.ts`: `strategy: config.adapter ? "database" : "jwt"` (https://github.com/nextauthjs/next-auth/blob/main/packages/core/src/lib/init.ts). Adapter without an explicit `strategy` means database sessions.
- **Adapter + Google + JWT works.** In the OAuth branch, `handleLoginOrRegister` runs the adapter (`getUserByAccount`, `createUser`, `linkAccount`), then with `useJwtSession` builds a token with `sub: user.id` and calls the `jwt` callback with the adapter user (callback/index.ts and handle-login.ts, same repo path `packages/core/src/lib/actions/callback/`). Docs: "even with a database, you can use JWT sessions" (https://authjs.dev/concepts/database-models). The Prisma adapter page shows the `jwt` strategy with an adapter for the edge split (https://authjs.dev/getting-started/adapters/prisma).
- **Do we need the adapter?** Not strictly. Without an adapter `handleLoginOrRegister` returns `{ user: _profile, account }` and persists nothing ("If no adapter is configured then we don't have a database and cannot persist data", handle-login.ts). Then `user.id` in the `jwt` callback would be the Google profile id and you would have to upsert your own `User` row. Since events need an FK to a DB user, the adapter is the lower-risk path (inferred). With the adapter, user and account rows are saved automatically on first sign-in (https://authjs.dev/concepts/database-models).
- **Credentials persists nothing by itself**: "By default, the Credentials provider does not persist data in the database"; hashing, rate limiting and reset are yours; validate with zod inside `authorize`; return `null` on failure (https://authjs.dev/getting-started/authentication/credentials). Registration is your own Server Action (no API route).
- **Prisma schema for the adapter**: `User` (unique `email`), `Account` (unique `[provider, providerAccountId]`), `Session` (unique `sessionToken`), `VerificationToken` (unique `[identifier, token]`); `@map()` allowed (https://authjs.dev/getting-started/adapters/prisma). Add your own `passwordHash String?` to `User` (null for Google-only users). Keep `Session`/`VerificationToken` models unless you test removing them (uncertainty #3).
- **Adapter docs lag Prisma 7.** The page documents Prisma with Accelerate and `prisma init --output ./src/generated/prisma` and says nothing about driver adapters. The adapter just takes a `PrismaClient` (`PrismaAdapter(prisma)`), so passing the Prisma 7 client should work (inferred; smoke-test it).

### Config split and proxy

- **Rename.** In Next.js 16 `middleware.ts` is deprecated and renamed to `proxy.ts` (export `proxy` or a default export). Codemod: `npx @next/codemod@canary middleware-to-proxy .`. Version table: "v16.0.0 Middleware is deprecated and renamed to Proxy. Proxy defaults to the Node.js runtime"; "v15.5.0 Middleware can now use the Node.js runtime (stable)" (https://nextjs.org/docs/app/api-reference/file-conventions/proxy, docs version 16.4.0).
- **Runtime.** "Proxy defaults to using the Node.js runtime. The `runtime` config option is not available in Proxy files. Setting the `runtime` config option in Proxy will throw an error." (same page). So on Next 16 Prisma, `pg` and native `bcrypt` are importable in proxy. Edge limits apply only if you stay on Next <= 15 `middleware.ts` with the Edge default.
- **Auth.js split.** `auth.config.ts` = providers only, no adapter; `auth.ts` = `...authConfig` + `PrismaAdapter` + `session: { strategy: "jwt" }`; `proxy.ts` makes its own `NextAuth(authConfig)` and exports `auth` as `proxy`. Docs note that Next.js 16+ runs proxy on Node so this workaround "may not be needed" (https://authjs.dev/guides/edge-compatibility). Prisma page: with `@prisma/client` >= 5.9.1 and JWT sessions no extra changes are needed as long as the middleware/proxy runs no DB queries (https://authjs.dev/getting-started/adapters/prisma).
- **Simple proxy.** `export { auth as proxy } from "@/auth"` plus an `authorized` callback returning `!!auth`; matcher excluding `api`, `_next/static`, `_next/image`, `favicon.ico`. "You should not rely on the proxy exclusively for authorization." (https://authjs.dev/getting-started/session-management/protecting).
- **Server Actions vs proxy.** "Server Functions are not separate routes... a Proxy matcher that excludes a path will also skip Server Function calls on that path... Always verify authentication and authorization inside each Server Function rather than relying on Proxy alone." (proxy page above).
- **Recommendation (inferred).** One `auth.ts` + a one-line `proxy.ts` that redirects anonymous users to `/login`; real checks via `auth()` in each action. Add `auth.config.ts` only to keep Prisma/bcrypt out of the proxy bundle.
- **Hashing library.** `bcryptjs@3.0.3` (pure JS) and `bcrypt@6.0.0` (native) are both current on npm. No first-party Auth.js guidance on the choice (uncertainty #10).

## 3. Session/user id in Server Actions and Components

- **`auth()`.** `const session = await auth()` in Server Components (https://authjs.dev/getting-started/session-management/protecting). It is "a universal method... works in Middleware, Server Components, Route Handlers, and API Routes" (https://authjs.dev/reference/nextjs). Auth.js pages do not show Server Actions explicitly, but every Next.js example does: `const session = await auth(); if (!session?.user) throw new Error('Unauthorized')` inside `"use server"` code (https://nextjs.org/docs/app/getting-started/mutating-data, https://nextjs.org/docs/app/guides/data-security).
- **Expose `user.id`** (https://authjs.dev/guides/extending-the-session):

```ts
callbacks: {
  jwt({ token, user }) {
    if (user) token.id = user.id   // `user` exists only at sign-in
    return token
  },
  session({ session, token }) {
    session.user.id = token.id
    return session
  },
}
```

  Auth.js also sets `token.sub` to the user id at sign-in (`defaultToken.sub` in callback/index.ts), so `token.sub` is an alternative (inferred).
- **TypeScript augmentation** (https://authjs.dev/getting-started/typescript; "any file included by your tsconfig.json"):

```ts
import { type DefaultSession } from "next-auth"
declare module "next-auth" {
  interface Session { user: { id: string } & DefaultSession["user"] }
}
declare module "next-auth/jwt" {
  interface JWT { id?: string }
}
```

- **Ownership pattern.** Derive the owner from the session, never from client input: `findFirst({ where: { id: itemId, ownerId: session.user.id } })` (https://nextjs.org/docs/app/guides/server-actions#security). Next.js recommends a `server-only` Data Access Layer with thin `"use server"` actions (https://nextjs.org/docs/app/guides/data-security#using-a-data-access-layer-for-mutations). Your rule "all DB logic in Server Actions" is compatible if each action starts with a shared `requireUserId()` helper.
- **signIn/signOut** can be called from `"use server"` form actions; `redirectTo` sets the destination; wrap `signIn` in try/catch, handle `AuthError`, rethrow everything else (the redirect is an exception) (https://authjs.dev/reference/nextjs). Failed credentials give `CredentialsSignin` (credentials docs above).

## 4. Account linking (Google email equals existing Credentials user)

- **Default.** "For security reasons, Auth.js does not automatically link OAuth accounts to existing accounts if the user is not signed in." The user sees `OAuthAccountNotLinked` (https://authjs.dev/reference/core/errors).
- **Source.** `handle-login.ts`: when no account matches `[provider, providerAccountId]` but a user with the same email exists: if `provider.allowDangerousEmailAccountLinking` the existing user is reused, otherwise `OAuthAccountNotLinked` is thrown; the comment says the check makes it "harder to hijack a user account using a 3rd party OAuth account" (https://github.com/nextauthjs/next-auth/blob/main/packages/core/src/lib/actions/callback/handle-login.ts).
- **Official wording.** Opt in only "when you trust the OAuth provider to have verified the user's email address" (errors page; same sentence in the source comment).
- **Safe linking**: automatic only when the user is currently signed in (https://authjs.dev/concepts/database-models).
- **Implications for EventsOn (inferred, with research):**
  - Google exposes `email_verified` in the profile; the docs suggest checking it in the `signIn` callback (https://authjs.dev/getting-started/providers/google).
  - The real risk is the Credentials side. If anyone can register `victim@x.com` with an attacker-chosen password without proving mailbox ownership, then enabling linking lets the victim's later Google login attach to the attacker-created user, and the attacker's password still works. This is "pre-hijacking", measured in Sudhodanan and Paverd, "Pre-hijacked accounts: An Empirical Study of Security Failures in User Account Creation on the Web", USENIX Security 2022 (35 of 75 services vulnerable): https://www.usenix.org/conference/usenixsecurity22/presentation/sudhodanan
  - Options: (a) keep the flag off, show a "sign in with your password, then connect Google" message, and implement linking from a signed-in settings page (the official default); (b) enable it only on Google and require verified email for Credentials sign-up (Auth.js provides no verification flow for Credentials, so you build it); (c) additionally reject in the `signIn` callback when `profile.email_verified !== true`.

## 5. Prisma

- **Versions** (npm registry): `@prisma/client` `latest` = **7.10.0**; `prisma` `latest` = `8.0.0-rc.22` while its `prev` tag = 7.10.0; `@prisma/adapter-pg` `latest` = 7.10.0 (https://registry.npmjs.org/@prisma/client, /prisma, /@prisma/adapter-pg). Prisma's v7 docs call Prisma 8 a "release candidate", say Prisma 7 "remains fully supported", and install with `@prisma/client@7` and `prisma@prev` (https://www.prisma.io/docs/orm/v7, https://www.prisma.io/docs/guides/v7/frameworks/nextjs). GitHub releases show only 8.0.0 release candidates at the top (https://github.com/prisma/prisma/releases). **Use Prisma 7.10.0 and pin `prisma@7.10.0`.**
- **Engines.** `@prisma/client@7.10.0`: Node `^20.19 || ^22.12 || >=24`, TypeScript `>=5.4.0` (npm registry). Next 16.4.0 needs Node >= 20.9.
- **Prisma 7 changes** (https://www.prisma.io/docs/orm/more/upgrade-guides/upgrading-versions/upgrading-to-prisma-7):
  - `prisma-client` generator replaces `prisma-client-js`; `output` is required; no generation into `node_modules`.
  - A driver adapter is required for every database (`new PrismaClient({ adapter })`, `@prisma/adapter-pg` for Postgres).
  - `prisma.config.ts` holds CLI config (schema path, migrations, datasource url, seed); env files are not auto-loaded (use `dotenv`).
  - ESM: `"type": "module"` and `"moduleResolution": "bundler"`.
  - `migrate dev` and `db push` no longer run `generate` or seeds.
  - `pg` has no default connection timeout via the adapter; stricter SSL validation (`P1010`).
- **Next.js setup** (https://www.prisma.io/docs/guides/v7/frameworks/nextjs, https://www.prisma.io/docs/orm/v7/prisma-client/setup-and-configuration/introduction):
  - `npm install @prisma/client@7 @prisma/adapter-pg dotenv pg`; dev: `prisma@prev tsx @types/pg`; `npx prisma init --output ../app/generated/prisma`.
  - Generator: `provider = "prisma-client"`, `output = "../app/generated/prisma"`.
  - `prisma.config.ts`: `import "dotenv/config"`, `defineConfig({ schema: "prisma/schema.prisma", migrations: { path: "prisma/migrations", seed: "tsx prisma/seed.ts" }, datasource: { url: env("DATABASE_URL") } })`.
  - `lib/prisma.ts` singleton: `PrismaClient` from the generated `client`, `new PrismaPg({ connectionString: process.env.DATABASE_URL })`, cached on `global` when `NODE_ENV !== "production"`, `export default prisma`.
  - `"postinstall": "prisma generate"` for deployments. The guide's sample package.json still lists Prisma 6; ignore it.
  - Caution: `https://www.prisma.io/docs/guides/nextjs` (unversioned) is the Prisma 8 / "Prisma Next" guide with a different API; use the `/v7/` URLs.
- **Enums.** `enum Role { USER ADMIN }` and `role Role @default(USER)` (https://www.prisma.io/docs/orm/v7/prisma-schema/data-model/models). Generated enum values use schema names, not `@map` values (upgrade guide above). Changing enum members needs a migration.
- **Search.** `where: { title: { contains: "prisma", mode: "insensitive" } }` is in the Client reference (https://www.prisma.io/docs/orm/v7/reference/prisma-client-reference, `contains` example) and the filtering page notes PostgreSQL case-insensitive modes (https://www.prisma.io/docs/orm/v7/prisma-client/queries/filtering-and-sorting). Combine `OR: [{title...},{description...}]` with `userId: session.user.id` in the same `where`. `%`/`_` typed by users act as LIKE wildcards in Postgres; escaping is on you (uncertainty #7).
- **Indexes** (https://www.prisma.io/docs/orm/v7/prisma-schema/data-model/indexes): composite `@@index([userId, startAt])` serves "one user's events in a date range". A B-tree cannot serve `ILIKE '%x%'`; Postgres `pg_trgm` GIN (`gin_trgm_ops`) supports `LIKE`/`ILIKE` (https://www.postgresql.org/docs/current/pgtrgm.html). Prisma's index page documents `raw("...")` operator classes for GIN but has no `gin_trgm_ops` example. Extensions are installed through an empty migration: `prisma migrate dev --create-only` then add `CREATE EXTENSION IF NOT EXISTS ...;` by hand (https://www.prisma.io/docs/orm/v7/prisma-schema/postgresql-extensions). So a trigram index would be hand-written SQL in a migration. Per-user tables are small, so start with `@@index([userId, startAt])` and add trigram only if measured (inferred).
- **Migrations.** `migrate dev` for development (uses a shadow database; your role needs permission to create databases); `migrate deploy` for production, CI and testing, which "does not rely on a shadow database" and should run in automated CI/CD (https://www.prisma.io/docs/orm/v7/prisma-migrate/workflows/development-and-production).

## 6. FullCalendar with App Router and MUI

- **Versions** (npm registry): `@fullcalendar/react` and `@fullcalendar/core` `latest` = **7.1.2** (react 7.1.2 published 2026-10-12; 7.0.0 on 2026-06-19). `@fullcalendar/react@7.1.2`: license MIT; peers `react`/`react-dom` `^17 || ^18 || ^19`, `temporal-polyfill ^1.0.1`; deps `@fullcalendar/core@7.1.2`, `@full-ui/headless-calendar@7.1.2`. The v6 line (`@fullcalendar/daygrid|timegrid|interaction|list|multimonth`) is at `6.1.21` (MIT); these have no v7 stable under their own names (`7.0.0-rc.0`/beta only).
- **v7 package structure** (https://fullcalendar.io/docs/upgrading-from-v6): "`@fullcalendar/daygrid` and many other standard packages removed and moved to `@fullcalendar/react/*` entrypoints"; `temporal-polyfill` is a required peer (not installed globally); event-source field renames (`classNames` -> `className`, ...); no bundled CSS and no `fc-*` classes by default. The 7.1.2 `package.json` exports: `.`, `./daygrid`, `./timegrid`, `./list`, `./multimonth`, `./interaction`, `./all`, `./locales/*`, `./skeleton.css`, `./themes/{classic,monarch,forma,pulse,breezy}` (+ palettes).
- **Install (v7)**: `npm install --save @fullcalendar/react temporal-polyfill`; `import FullCalendar from "@fullcalendar/react"`; views from `@fullcalendar/react/daygrid` etc.; always import `@fullcalendar/react/skeleton.css` plus a theme CSS and a palette; "must initialize your calendar with at least one plugin that provides a view" (https://fullcalendar.io/docs/react). If you prefer the long-established API, `@fullcalendar/react@6` + `@fullcalendar/daygrid|timegrid|interaction@6.1.21` is the conservative alternative.
- **`"use client"`.** The docs page does not mention it. I downloaded `@fullcalendar/react@7.1.2` with `npm pack` and found **no file containing `use client`**. Treat it as a client-only React component: import it only inside your own file that starts with `'use client'` (conclusion from package contents).
- **License.** Standard (non-premium) plugins and the `fullcalendar` bundle are released under the **MIT license**; premium plugins and the scheduler bundle need a commercial license, with free options for registered non-profits and for AGPLv3-compliant open-source projects; "As of v7, AGPLv3 replaces GPLv3" for those premium open-source options (https://fullcalendar.io/license; also https://fullcalendar.io/docs/upgrading-from-v6: "Standard packages remain MIT"). Day grid, time grid, list, multi-month and interaction are standard, so there is no GPL issue for EventsOn. Premium examples (not needed): resource timeline; v7 scheduler is `@fullcalendar/react-scheduler`.
- **MUI.** `@mui/material` `latest` = 9.5.0 (v7.3.11 and v6.5.0 also published). `@mui/material-nextjs@9.5.0` exports `v13..v16-appRouter` and peers `next ^13..^16`, `@emotion/cache`, `@emotion/react`, `@emotion/server`. Setup: `npm install @mui/material-nextjs @emotion/cache`; wrap `<body>` children in `AppRouterCacheProvider` from `@mui/material-nextjs/v16-appRouter`; define the theme in a file with `'use client'`; for Next 16, a `Link` passed to a MUI `component` prop may need a `'use client'` re-export wrapper (https://mui.com/material-ui/integrations/nextjs/). FullCalendar does not depend on MUI; style it via its CSS/theme variables.
- **Rendering events from a Server Action.** Client components can call imported Server Actions from event handlers or `useEffect` (https://nextjs.org/docs/app/getting-started/mutating-data, "Event Handlers"/"useEffect"). So the client calendar calls `getEventsInRange(startISO, endISO)` (in a `"use server"` file) and hands the array to FullCalendar. Return plain DTOs (`id`, `title`, `start`/`end` ISO strings, `allDay`), not Prisma rows (https://nextjs.org/docs/app/guides/data-security#controlling-return-values); `Date` is a supported argument type but encoding details are framework-defined (https://react.dev/reference/rsc/use-server). Query by `userId` from `auth()` and by overlap with `[start, end)`.
- **Visible-range fetching.**
  - `events` function: `function(fetchInfo, successCallback, failureCallback)`; `fetchInfo` has `start`, `end` (exclusive), `startStr`, `endStr`, `timeZone`; a Promise may be returned instead of using callbacks; it is called when the calendar needs new data such as prev/next or view change (https://fullcalendar.io/docs/events-function). Cleanest: `events: (info) => getEventsInRange(info.startStr, info.endStr)`.
  - `datesSet(dateInfo)`: `start`, `end` (exclusive), `startStr`, `endStr`, `timeZone`, `view`; use it if you manage the range in React state (https://fullcalendar.io/docs/datesSet).
  - Caveat: Next.js sends Server Actions one at a time per client, so rapid navigation queues; do not rely on `Promise.all` parallelism (https://nextjs.org/docs/app/guides/server-actions#sequential-dispatch-on-the-client). Mitigate with ignoring stale responses and fetching a padded range.
- **Click handlers.**
  - `dateClick` needs the interaction plugin ("In order for this handler to fire, you must load the `interaction` plugin"); arg: `date`, `dateStr`, `allDay`, `dayEl`, `jsEvent`, `view` (https://fullcalendar.io/docs/dateClick). Use it to open an MUI Dialog for a new event prefilled with `dateStr`.
  - `eventClick` does not require the interaction plugin; arg: `event`, `el`, `jsEvent`, `view` (https://fullcalendar.io/docs/eventClick). Put the DB id in `event.id`, and have the Server Action re-check ownership.
  - After create/update/delete, refetch the visible range (the v7 refetch API was not confirmed; uncertainty #5).

## 7. Server Actions: validation, authorization, forms, revalidation

- **Public endpoints.** "A Server Action runs as a POST request against the page that invokes it... Treat every action as an untrusted entry point."; authenticate and authorize inside every action, validate inputs, constrain return values (https://nextjs.org/docs/app/guides/server-actions#security). Also: "Server Functions are reachable via direct POST requests... Always verify authentication and authorization inside every Server Function" (https://nextjs.org/docs/app/getting-started/mutating-data). A page-level check does not cover the actions (https://nextjs.org/docs/app/guides/data-security#authentication-and-authorization).
- **Arguments are untrusted**: "Arguments to Server Functions are fully client-controlled... validate and escape arguments" (https://react.dev/reference/rsc/use-server). Schema validation checks shape only; a well-formed id can belong to someone else, so look up by `{ id, ownerId: session.user.id }` (Next server-actions guide, `completeItem` example). Use `updateMany`/`deleteMany` with `{ id, userId }` or `findFirst` first, to avoid IDOR (data-security guide).
- **Built-in protections**: encrypted non-deterministic action IDs, dead-code elimination of unused actions, Origin/Host CSRF check, 1MB body limit, encrypted closure variables (https://nextjs.org/docs/app/guides/data-security). For multi-instance self-hosting set `NEXT_SERVER_ACTIONS_ENCRYPTION_KEY`.
- **zod.** Next.js recommends zod/valibot with `safeParse` in the action and returning errors (https://nextjs.org/docs/app/guides/forms#form-validation). **The sample uses zod 3 APIs** (`invalid_type_error`, `.flatten()`). Current zod is **4.6.7** (npm). In zod 4 `invalid_type_error`/`required_error` were dropped (use `error`), `.flatten()` is deprecated in favor of `z.flattenError(error)`, and `z.string().email()` is deprecated in favor of `z.email()` (https://zod.dev/v4/changelog, https://zod.dev/error-formatting).
- **Forms.** `const [state, formAction, pending] = useActionState(action, initialState)`; the action receives `(prevState, formData)`; the form component must be a Client Component (https://nextjs.org/docs/app/guides/forms#validation-errors). `useFormState` is the older name; on React 19.3 use `useActionState` from `react` (the Next docs use only `useActionState`). For non-form triggers wrap in `startTransition` (mutating-data page). `useFormStatus` is available for a submit button.
- **Revalidation.** `revalidatePath(path, type?)` in a Server Function "Updates the UI immediately (if viewing the affected path)" (https://nextjs.org/docs/app/api-reference/functions/revalidatePath). `updateTag` = read-your-own-writes (Server Actions only); `revalidateTag` = stale-while-revalidate, no immediate re-render in the action response; `refresh()` refetches the current route without invalidating cache (https://nextjs.org/docs/app/guides/server-actions#choosing-a-cache-update). Call them before `redirect()`, which throws. Because the calendar data comes from a client-invoked action rather than a cached Server Component, `revalidatePath` will not refresh it: refetch on the client after each mutation (inferred).
- **Reads via actions from client components.** Works (handlers/`useEffect`), but the docs frame Server Functions as "designed for server-side mutations" with one-at-a-time client dispatch and suggest Server Components or Route Handlers for parallel reads (https://nextjs.org/docs/app/getting-started/mutating-data, https://nextjs.org/docs/app/guides/server-actions). Route Handlers are ruled out by your constraint, so accept the trade-off; for first paint, call the same query function from a Server Component.
- **Return values** are serialized to the client: return DTOs, never Prisma rows with `passwordHash` (data-security guide). Rate-limit login/register (https://nextjs.org/docs/app/guides/data-security#rate-limiting; Auth.js leaves Credentials rate limiting to you).

## 8. Testing Server Actions with Vitest on real Postgres

No first-party doc covers "testing Server Actions" directly; below is built from first-party mechanics (items marked inferred).

- **Vitest version.** `vitest` `latest` = **5.0.4** (2026-10-12), Node `^22.12 || ^24 || >=26`; tag `V4` = 4.1.11 (npm registry). Next's Vitest guide says Vitest does not support async Server Components; unit-test async functions and use E2E for async components (https://nextjs.org/docs/app/guides/testing/vitest). Use `environment: 'node'` for action tests and `vite-tsconfig-paths` for `@/` aliases.
- **Actions are plain async functions in tests** (inferred: `"use server"` is a module directive per https://react.dev/reference/rsc/use-server, so Vitest just runs the function). No request context exists, so mock request-bound modules.
- **Mock `auth()` at the boundary.** `vi.mock('@/auth', () => ({ auth: vi.fn() }))`, then per test `vi.mocked(auth).mockResolvedValue({ user: { id: 'u1' }, expires: '...' })` or `mockResolvedValue(null)`. `vi.mock` is hoisted; wrap in `vi.fn()` for call tracking; `importOriginal` for partial mocks (https://vitest.dev/guide/mocking/modules). Test both unauthenticated and cross-tenant (user B cannot read/update/delete user A's event).
- **Mock `next/cache` / `next/navigation`.** Next's `updateTag` throws when there is no work store (`if (!workStore || ...) throw new Error(...)`, https://github.com/vercel/next.js/blob/canary/packages/next/src/server/web/spec-extension/revalidate.ts; I read that function only, the others are analogous: uncertainty #9). So `vi.mock('next/cache', () => ({ revalidatePath: vi.fn(), revalidateTag: vi.fn(), updateTag: vi.fn() }))`. `redirect` throws a control-flow exception by design (https://nextjs.org/docs/app/getting-started/mutating-data); mock `next/navigation` or assert the throw.
- **Real Postgres.** Use a dedicated test database/container with its own `DATABASE_URL`; run `prisma migrate deploy` once in Vitest `globalSetup` ("before the test workers are created", values passed via `project.provide`/`inject` because setup runs in a different global scope: https://vitest.dev/config/globalsetup). `migrate deploy` needs no shadow database (Prisma migrate workflow page, section 5). Prisma 7 does not auto-load `.env` and needs `prisma generate` first. Isolate tests by truncating tables in `beforeEach` or by unique users per test; run files serially when they share one DB (Vitest `fileParallelism`/`maxWorkers`, not read in detail). Point the `lib/prisma.ts` singleton at the test URL before import and `$disconnect()` in `afterAll`.
- **Keep Auth.js out of unit tests**: export `authorize`/credential-checking logic as a plain function and test it directly (inferred).
